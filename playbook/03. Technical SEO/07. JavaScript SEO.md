# JavaScript SEO

> The discipline of making sure JavaScript-rendered content is actually visible to Google. On JS-heavy sites (Next.js, React, Vue without SSR), the gap between what users see and what Googlebot crawls is the difference between ranking and not existing.

## What it is

JavaScript SEO covers the technical decisions that determine whether Googlebot can render and index content that's loaded via JavaScript rather than served as static HTML. Modern frameworks (React, Vue, Angular, Next.js, Remix, Nuxt) rely heavily on client-side or hybrid rendering, and the way each handles content delivery has direct SEO consequences.

Three rendering modes you need to know:

- **CSR (Client-Side Rendering)** — server returns a near-empty HTML shell; the browser runs JavaScript to fetch data and build the page. Pure CSR (a default `create-react-app` or Vite SPA) is hostile to SEO unless you add prerendering.
- **SSR (Server-Side Rendering)** — server runs the JavaScript and returns fully-rendered HTML. Googlebot sees the same thing the user sees on first paint. Best-in-class for SEO. Next.js and Nuxt default here.
- **ISR / SSG (Incremental Static Regeneration / Static Site Generation)** — content is pre-rendered at build time (or on demand) and served as static HTML. Excellent for SEO. Next.js, Astro, Gatsby support this.

For Field & Sun on Shopify, JS rendering is mostly handled by the platform — Liquid templates output server-rendered HTML, and the SEO concerns are minimal. JavaScript SEO becomes critical when a brand moves to a headless front-end (Hydrogen, Next.js + Shopify Storefront API), or when third-party widgets inject content that's only visible after page load.

## Why it matters

Three reasons. First, **Googlebot has limits on JavaScript rendering**. Google does run JS, but on a delay (the "second wave" of indexing) and with a finite render budget. Pages that depend on heavy client-side hydration to display their main content are at material risk of being indexed empty — Googlebot crawls the shell, queues the JS for rendering, and may take days or weeks to come back.

Second, **third-party JS-injected content rarely gets indexed reliably**. Reviews loaded via Yotpo's widget. Product Q&A from a chat tool. FAQ accordions hydrated by an app. If the content lives in a JS payload that fires after first paint, treat it as "may or may not be in the index."

Third, **Single-Page Applications (SPAs) without server rendering struggle with discovery**. URLs change via the History API but Googlebot can crawl them only if they're linked from server-rendered pages with real `<a href>` links. Bare-SPA architecture is borderline-impossible to make rank.

For most ecom on a CMS like Shopify, this category is a watch-out, not a blocker. For brands moving headless, this becomes a P0 concern.

## Core concepts

- **Source HTML vs rendered DOM.** *Source* is what the server returns to a `curl` request. *Rendered DOM* is what the browser shows after JS executes. Googlebot uses both: source for first-pass indexing, rendered for the second-pass refresh. The gap between them is the JS-SEO surface.
- **First Contentful Paint (FCP) and main-content visibility.** Critical-path content (H1, main copy, product details, internal links) should be in the source HTML, not injected post-load. If FCP is empty, Google's first-pass crawl sees nothing.
- **Internal links must be `<a href>`, not click-handlers.** Googlebot follows `<a href="/x">`. It does not follow `<div onClick={navigate('/x')}>`. The History API lets SPAs maintain state without page reloads, but the *links* must still be real anchors.
- **Hydration vs rendering.** Hydration is the process where client-side JS attaches to server-rendered HTML and "wakes it up." Done right, the server delivers visible content immediately and the page becomes interactive after JS loads. Done wrong, the server delivers a blank shell and "hydration" is actually rendering for the first time on the client.
- **Dynamic Rendering (Google's deprecated workaround).** Serving a different version of the page to bots vs users. Google deprecated this guidance in 2024 in favour of SSR / SSG. Avoid.
- **Prerendering services (Prerender.io, Rendertron).** Workarounds for legacy SPAs. Generate static HTML for bot user-agents on demand. Functional but a band-aid; long-term move to SSR/SSG.
- **JavaScript redirects vs HTTP redirects.** `window.location = '/x'` is a JavaScript redirect. Googlebot follows them, but with a delay and unreliably. HTTP 301/302 are always preferred.
- **The "View Page Source" vs "View Computed DOM" test.** Quickest manual diagnostic: right-click → View Source. If the H1, main copy, and primary internal links aren't there, you have a JS rendering problem.

## A worked example

> **Scenario:** A hypothetical brand runs a headless Next.js storefront talking to Shopify Storefront API. PDPs use Next.js' `getStaticProps` (SSG) for the main product details — fine. But customer reviews are loaded via the Yotpo React widget after first paint, and the FAQ accordion is fetched via a client-side API call to a custom CMS. GSC shows: PDPs are indexed but the review content and FAQ content isn't appearing in any cached version. SERPs miss FAQ rich snippets entirely.
>
> **Step 1.** Diagnostic. View source on the PDP. Confirm: title, H1, product description, price are all in source HTML — good. Reviews and FAQ section render with `<div id="yotpo-reviews">` and `<div id="faq-loading">` placeholders — content gets injected by JS only.
>
> **Step 2.** Use Google's URL Inspection tool. View "Crawled page" → "View tested page" → check the rendered HTML Google captured. Reviews are there (Google did render the second-pass, after a delay). FAQ section is empty (the FAQ API call failed during Googlebot's render — probably because of timing or rate-limiting).
>
> **Step 3.** Fix the FAQ section. Move FAQ content from a client-side fetch to `getStaticProps` so it ships in the initial HTML. Validate FAQPage schema against the now-server-rendered FAQ.
>
> **Step 4.** Reviews are working but slowly. Two options: (a) accept the delay, (b) move review content into Storefront API and pre-render review excerpts at build time. Most teams pick (a) since reviews refresh constantly anyway and the delay is acceptable.
>
> **Step 5.** Re-submit. After 14-30 days, FAQ rich snippets appear in SERPs; review structured data is consistently picked up.

## How to do it

1. **Identify if you have a JS-rendering problem at all.** On Shopify default themes, WordPress / WooCommerce default themes, Webflow — usually no. On Next.js / Hydrogen / Remix / custom React or Vue stacks — yes, audit. The audit cost is low; just confirm.
2. **View the source HTML of priority pages.** Right-click → View Source on PDPs, top blog posts, collection pages. Look for: H1, primary copy, internal links, structured data. Anything missing from source is at risk.
3. **Use GSC URL Inspection's "Test live URL" → "View tested page"** to see exactly what Googlebot rendered. This is ground truth — it shows you what Googlebot put in its index after running your JavaScript.
4. **Identify the gap between source HTML and rendered DOM.** Anything in the rendered DOM but not in source is JS-injected. Decide per element: critical for SEO (H1, main copy, FAQ schema content, internal links — must be in source) vs nice-to-have (chat widget, recommended products, social proof — fine to JS-inject).
5. **Move SEO-critical content to server-rendered HTML.** In Next.js: use `getStaticProps` / `getServerSideProps` for content that should be in the initial HTML. Avoid pure client-side `useEffect` data fetches for primary content.
6. **Audit internal links.** Confirm all primary navigation, breadcrumbs, related-content links, and pagination use `<a href>` — not just `onClick` handlers with `router.push()`. Even with Next.js `<Link>`, the underlying anchor must exist.
7. **Audit third-party widgets.** Each widget that injects content (reviews, FAQ, chat, related products) is a JS-rendering risk. For each: is the content critical for SEO? If yes, find a server-side alternative or accept the second-pass-indexing delay.
8. **Validate redirects.** All page-level redirects should be HTTP 301/302, not JavaScript `window.location` redirects.
9. **Monitor GSC's "Crawled – currently not indexed" bucket.** A spike here on a JS-heavy site is usually a rendering problem. Cross-reference with the URL Inspection tool to confirm.

## Common pitfalls

- **Assuming Google "runs JavaScript so we're fine."** Google does run JS, but on a delay, with a budget, and unreliably for content fetched via post-load API calls. Critical content belongs in source HTML.
- **Internal links as `onClick` handlers.** Bots can't follow them. Always `<a href>` underneath any navigation abstraction.
- **JavaScript redirects.** Slow and unreliable. Use HTTP redirects.
- **FAQ / Review widgets that inject content via JS.** Often the cause of FAQPage schema not earning rich results — Google can't reconcile the schema with the (still-empty) rendered DOM at first-pass crawl.
- **Loading critical content from a separate API call after page load.** That's a JS-rendering risk. Move to SSR or SSG.
- **Pure SPA architectures for marketing pages.** PDPs, collection pages, and blog posts should be SSR'd or pre-rendered. Pure CSR for these is borderline-impossible to rank.
- **Relying on Dynamic Rendering long-term.** Google deprecated this guidance. Move to SSR / SSG.
- **Not testing on a JS-heavy site after every theme / framework upgrade.** Hydration patterns can change between Next.js versions. Regress testing matters.
- **Ignoring the rendered DOM in URL Inspection.** That's the single most diagnostic view Google gives you. Use it.
