# A/B Testing

> Disciplined experimentation for SEO-driven traffic. SEO-safe testing patterns, sample-size discipline, what to test vs. what's not worth testing. The discipline that closes the loop on what actually moves conversion.

## What it is

A/B testing is the practice of running controlled experiments where two or more variants of a page (or component) are shown to different visitor groups simultaneously, with conversion / engagement measured to determine which variant wins. In the SEO context, it's how teams resolve "is this design change actually moving conversion?" beyond hypothesis. Done well, A/B testing closes the loop between design decisions and conversion outcomes; done poorly, it produces underpowered tests, false positives, and SEO-damaging cloaking issues.

For Field & Sun, A/B testing is the discipline that turns "we think the new pillar above-fold is better" into "the new pillar above-fold lifts pillar→PDP CTR by 12% (95% confidence)" — or kills the change before it ships site-wide. The infrastructure cost is moderate ($100-500/mo for Optimizely / VWO / Convert / Google-Optimize-replacement); the operational cost is the discipline of sample-size patience.

## Why it matters

Three reasons. First, **A/B testing resolves design-decision ambiguity**. Many UX design changes are ambiguous — could go either way. Without testing, the team ships hunches; with testing, they ship confirmed winners. Over a year, the difference is meaningful.

Second, **A/B testing prevents shipping losers**. A design change that *feels* better but actually hurts conversion happens frequently. Testing catches the loser before it ships site-wide and damages revenue for months while nobody notices.

Third, **A/B testing builds team discipline**. Teams that test learn what actually works for their audience — not generic best-practices but their-brand-specific patterns. That learning compounds over years.

The trade-offs: A/B tests need traffic for statistical power (5-15k visitors per variant typical for ecom-conversion tests), take 2-4 weeks to reach conclusion, and require infrastructure + operational discipline. Brands with low traffic on individual templates can't reasonably test every change; for those, design discipline + post-deployment measurement is the better pattern.

## Core concepts

- **Statistical power.** The probability that the test will detect a true effect. Higher power = larger sample size needed. Most A/B testing tools auto-calculate; teams under-spec by accepting underpowered tests as "tied."
- **Significance level.** Conventional 95% confidence (p < 0.05). One in 20 wins is a false positive even at this level; running too many tests in parallel inflates false-positive rate.
- **Minimum detectable effect (MDE).** The smallest effect size the test can reliably detect with the available sample. Calculate before running; if MDE > expected effect, the test is underpowered.
- **Sample-size pre-registration.** Decide before the test how big the sample will be; stop when reached. Peeking at results mid-test + stopping early inflates false-positive rate dramatically.
- **A/A testing.** Run two identical variants against each other to validate the test infrastructure. ~95% of variant-A vs variant-A tests should show no significant difference; if more than that show "significance," there's an instrumentation bug.
- **Multivariate vs A/B.** A/B = two variants. Multivariate = many factors tested simultaneously. Multivariate needs much larger sample; for most brands, sequential A/B is the right pattern.
- **SEO-safe testing patterns.** Variants served to all visitors (including Googlebot) consistently; canonicals correct; no cloaking. Most modern A/B tools handle this automatically; verify.
- **Cloaking risk.** If A/B tool serves different content to crawlers vs users, Google penalises. Avoid: server-side rendering hides this risk; client-side testing usually fine if implemented correctly.
- **Significance vs business significance.** A 1% lift may be statistically significant in a large test but not worth the engineering cost of shipping. Decide minimum business-significance threshold upfront.
- **What to test.** High-impact above-fold changes; primary CTA changes; major flow restructures; pricing / merchandising changes; high-traffic templates. **What not to test:** low-traffic pages (insufficient sample), bug fixes (just ship), legal-required changes (just ship), obvious wins (just ship), brand-voice violations (just ship the right brand voice).

## A worked example

> **Scenario:** Field & Sun's UX design review surfaced 3 candidate design changes for the mineral-sunscreen pillar: (1) replace generic hero with three-skin-tone-test imagery, (2) reduce above-fold CTAs from 4 to 1 primary, (3) add table-of-contents sidebar linking to spokes. The pillar gets ~4,200 visitors/mo; the team wants to test before shipping site-wide.
>
> **Step 1.** Run `plan-ab-test`. Skill produces test plan including hypothesis, variants, sample-size calculation, significance threshold, SEO-safety checks, runtime, success criteria.
>
> **Step 2.** Output:
>
> - **Test 1 (hero variant):** primary metric = pillar→PDP CTR. Current baseline 5.1%. MDE 1.5pp (relative ~30% lift). Sample needed: ~6,000 visitors per variant (12,000 total) for 95% confidence. Runtime estimate: ~3 weeks at current traffic.
> - **Test 2 (CTA reduction):** sequential to test 1; can't run simultaneously without affecting test 1's result.
> - **Test 3 (TOC sidebar):** can run as multivariate component overlapping test 1 if isolated — but recommend sequential for cleaner attribution.
> - **SEO-safety:** Optimizely client-side rendering preserves canonical + crawler-served content. A/A test pre-launch confirms instrumentation.
> - **Decision rules:** if winner ≥1.5pp at 95% confidence → ship; if no significant difference → keep current; if loses by ≥1pp → kill.
> - **Risks:** simultaneously running multiple ambiguous tests on same page muddies signal; sequence them.
>
> **Step 3.** Tests run sequentially over 9 weeks. Test 1 winner: three-skin-tone hero +12% pillar→PDP CTR (significant). Test 2 winner: single-primary CTA +6% (significant). Test 3: TOC sidebar +3% (not significant at 95% with the smaller effect; ship anyway because business-significance threshold met and below-fold engagement is up).

## How to do it

1. **Identify candidate tests.** Hypotheses from UX design review, traffic-pattern analysis, conversion-funnel diagnosis, or stakeholder requests.
2. **Filter for testability.** Page traffic ≥5k visitors/mo; expected effect ≥1pp on conversion; not bug-fix / legal-required / obvious-win.
3. **Prioritise by impact + clarity.** High-impact + ambiguous direction tests first. Low-impact + obvious wins → just ship.
4. **Run `plan-ab-test`.** Skill produces the test plan.
5. **Set up infrastructure.** Optimizely / VWO / Convert / etc. Verify SEO-safety (no cloaking, canonical preserved). Run A/A test as instrumentation check.
6. **Pre-register sample size + decision rules.** Document before launch. No mid-test peeking + stopping.
7. **Launch.** Confirm both variants serving correctly; analytics events firing.
8. **Wait for sample.** Don't peek; don't stop early.
9. **Analyse on-end.** Significance + effect size + business-significance check. Decide ship / kill / keep current.
10. **Document the result.** Decisions log in CLAUDE.md; learnings for future tests.
11. **Run sequential tests.** Build a backlog; cycle through.
12. **Quarterly review.** Test win rate, learnings, infrastructure improvements.

## Common pitfalls

- **Underpowered tests.** Running tests on traffic too low to detect the expected effect. Calculate sample size before; if traffic is insufficient, don't test (pick a higher-traffic page or a larger expected effect).
- **Mid-test peeking + stopping.** Inflates false-positive rate. Pre-register sample + run to completion.
- **Multiple simultaneous tests on same page.** Muddied signal; can't attribute to specific change.
- **Testing obvious wins.** "Should we add Add to cart button on PDP?" — just ship; don't test.
- **Testing low-impact changes.** "Should we change the button colour from #1234 to #1245?" — won't reach significance; not worth the effort.
- **No SEO-safety check.** Some A/B tools serve crawlers differently → cloaking signal to Google.
- **Cherry-picking metrics.** "It lost on conversion but gained on engagement" — pre-specify the success metric.
- **Significance ≠ business significance.** 0.5% lift at 95% confidence may not be worth the engineering cost.
- **Running tests on low-traffic pages.** Insufficient sample; either skip or aggregate similar templates.
- **No decisions log.** Without recording test outcomes, learnings don't compound.
- **A/B testing every change.** Some changes don't warrant tests (bug fixes, brand corrections, legal changes). Test where it's load-bearing.
